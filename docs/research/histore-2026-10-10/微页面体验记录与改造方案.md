# HiStore 微页面体验记录与项目改造方案

建议在现有微页面发布底座上，优先加强可视化编辑、商品导购组件和页面复用。HiStore 最有价值的参考是“组件库、手机画布、属性面板、统一内容选择器”的运营工作方式，以及商品和营销数据直接接入页面的能力。

第一批交付建议包含图文导航、商品列表、标题文字、图片广告、可视化热区、即时效果预览和页面复制；固定宫格紧随其后。完全自由布局、任意 HTML 和任意外链不进入默认范围。新增能力需要先形成产品规格增量，再同步接口和工程契约。本方案是评审建议，不替代现有产品规则。

## HiStore 的微页面能力

### 页面管理

列表提供微页面、草稿箱两个页签，支持关键字、创建时间筛选及分页。微页面行展示复制、编辑、推广、设为主页、删除等入口；当前主页行标有微商城首页、H5 首页、App 首页。草稿箱行也有推广入口，但草稿实际可访问范围尚未验证。

推广弹窗包含小程序与 H5 路径选择、海报与微信好友样式、分享标题、描述、图片、页面路径，以及推广海报和推广码下载入口。这提示项目后续可以将页面分享资料与装修内容分别配置，但二维码有效性必须单独进行平台验证。

### 编辑工作方式

编辑器采用左侧组件库、中间手机画布、右侧配置面板。拖入组件后，右侧切换为对应属性。点击组件内容可重新选择配置对象。单击左侧商品名称没有添加组件，拖入后成功，说明项目可提供“点击添加＋拖拽”的双入口以降低首次使用门槛。

组件管理显示当前组件清单，说明文字标注支持拖拽排序和点击定位；同时提供清除组件和单项删除入口。底部固定操作为上架、保存并继续、保存为草稿。按钮语义和实际持久化关系需要进一步测试，不能仅按名称认定状态转换。

页面设置包含名称、Logo、背景图片和颜色等。页面提示配置尺寸按 750 像素设计图的一半计算。项目宜使用统一设计单位并由终端转换，避免让运营人员理解多种换算口径。

### 组件覆盖

基础组件共 12 项：标题文本、商品、图片广告、图文导航、富文本、魔方、自由布局、辅助空白、商品搜索、公告、秒杀矩阵、新人专区。

营销组件共 9 项：直播、视频号直播、优惠券、膨胀券、限时折扣、拼团、秒杀、积分商品、社区话题。此次对商品、导航、魔方、自由布局、优惠券进行了配置体验；其余组件只确认菜单存在。

| 组件或工具 | 已确认能力 | 对项目的价值 |
| --- | --- | --- |
| 商品 | 单组或多组、指定商品或分类；分类来源有排序和数量；大图、双列、三列、详细列表、一大两小、横向滑动 | 运营可直接选品，减少商品拼图维护 |
| 商品样式 | 背景、边距、间距、圆角、图片比例和填充；名称、价格、活动标签、销量、卖点、购买按钮等选项 | 先保留少量稳定样式，避免属性过多 |
| 图文导航 | 添加图片、标题和链接；图片或文字导航；间距、高度、固定或横滑、颜色和圆角 | 分类入口和活动入口不再嵌入一张大图 |
| 魔方 | 多种固定模板，选择槽位后配置图片、标题、链接和间距 | 活动入口视觉多样，结构仍然受控 |
| 自由布局 | 可添加多类子组件，最小高度、内边距及 8 像素网格吸附选项 | 能力强，增加嵌套、碰撞和端适配成本 |
| 优惠券 | 手动添加或自动获取；自动模式有活动数量；大图或横滑；可检索优惠券和进入管理 | 页面消费营销域数据，减少重复配置 |
| 链接选择器 | 功能页面、商品、微页面、分类、品牌、营销活动、文章、问卷、外链、电话、直播分类 | 所有入口统一选目标，避免手填地址 |

商品面板的设置项较多，适合按“内容、布局、样式、高级”分组并提供默认样式。当前窗口较窄时，手机预览与配置面板出现空间拥挤；项目编辑器应在桌面保持完整画布，并允许折叠外围导航。

## 推荐的编辑器结构

页面管理入口继续区分首页和微页面。在微页面列表中显示名称、是否已发布、线上修订、草稿是否有更新、更新时间，并提供编辑、复制、预览、历史和分享路径。

编辑器左侧按基础展示、商品导购、营销三个分组列出组件，支持点击添加和拖拽添加。中间为按移动端比例显示的画布；选中组件后同时高亮对应大纲和右侧面板。右侧将内容、布局、样式分组，默认只展开内容。大纲支持组件定位、显隐和排序；复杂页面避免全部配置同时展开。

顶部展示页面名称、保存状态、草稿修订与线上版本；底部提供保存草稿、校验并预览、发布。即时效果用于编辑反馈，必须明确显示“未通过发布校验”。预览模式中区分选择组件和体验跳转，避免运营点击商品时意外离开编辑器。

撤销与重做只处理当前编辑内容，不能撤销已发布结果；发布回退继续走历史版本入口。离开未保存页面应提示，自动保存可随后加入且只写草稿，并沿用修订冲突检查。

## 分阶段交付

### 第一阶段 编辑效率与核心导购

目标是运营不依赖整页拼图，就能搭建品牌首页和分类活动专题。分两个切片交付：先完成即时效果预览、画布选择、可视化热区、组件复制、撤销与排序；再增加标题文字、图片广告、图文导航和商品列表，最后加入页面复制。

| 新增组件 | 首批范围 | 关键约束 |
| --- | --- | --- |
| 标题文字 | 主标题、副标题、对齐、字号枚举、颜色 | 文本长度限制，不执行 HTML |
| 图片广告 | 单图、受控比例、素材和站内跳转 | 与轮播区分，图片失败兜底 |
| 图文导航 | 图片或文字、固定列数、顺序、站内目标 | 首批不开放任意外链；缺图或失效目标有提示 |
| 商品列表 | 手动选品或分类来源；双列、列表、横滑三种样式；名称与价格展示 | 配置只存商品引用或查询条件，不保存价格和库存真相 |
| 页面复制 | 从已有页面草稿或线上版本创建新草稿，明确选择来源 | 新页面身份、组件身份独立；不复制发布指针、发布权限或历史 |

商品选品粒度必须先明确。当前基线与 SPU/共享库存分支不同，不能在本方案中默认已经合并 SPU。若后续以 SPU 为展示单位，应由商品域提供聚合展示及规格选择入口；若仍以当前商品实体为单位，先沿用对应公开 DTO。商品卡展示、选规格、报价和库存须保持一致，不能汇总共享库存池 SKU 的可售数。

### 第二阶段 布局与运营复用

加入固定宫格/魔方、辅助空白、主题预设和组件组合。宫格首批提供双列、三列、四宫格、一大两小等受控模板，槽位绑定图片与站内链接。

提供品牌首页、分类导购、活动专题三个模板。应用模板产生独立草稿快照，模板更新不自动修改线上页面。页面列表增加搜索与业务标签。分享标题、描述和封面可配置；小程序码生成只有在对应平台服务接入和验证后才作为可用功能交付。

### 第三阶段 营销与发布管理

优先接入既有权益域的优惠券列表及领取结果，配置只存活动引用或受控查询条件，领取资格、额度、有效期和核销规则继续归权益域。未登录、已领、领完、过期、无资格和请求失败均需有状态。

新增发布差异摘要、失效引用检查报告与兼容性报告。定时发布、页面下架及自动活动切换需要另外定义时区、任务幂等、撤销、目标引用失效和异常恢复规则，不能直接并入当前发布接口。

秒杀、拼团、直播、积分商品等按对应业务域和平台成熟度分别接入。自由画布单独评审嵌套深度、定位方式、小屏与长文适配、素材与链接扫描及旧版本回退。富文本如有实际需求，优先受控文本块；后续富文本只允许明确标签与素材绑定，不支持脚本、任意样式和任意外链。

## 技术改造边界

采用组件注册表统一描述类型、版本、默认配置、字段校验、编辑面板、预览器、终端渲染、素材引用和链接提取。三端保持契约一致，但不强求 Vue 与微信原生小程序复用同一套 UI 实现。通过相同配置样例做契约和渲染验证。

配置继续采用页面级 schemaVersion，补充组件版本与运行时所需能力；不要直接将新字段塞入当前严格校验的 schemaVersion 1。旧配置默认行为保持不变，迁移产生新的草稿或版本，保留原始快照。

新增组件需要先部署支持它的后台和小程序运行时，再开放配置发布。服务端校验已验证的运行时能力，不能信任前端传来的“支持”标记；旧客户端如何收到降级内容或被限制访问必须有明确策略。首次增加组件仍涉及代码版本渠道发布，后续同组件内容调整才继续独立于代码发布。

商品和权益组件通过所属域的有界只读查询批量获取数据，避免逐组件逐商品请求。图片延迟加载，商品数量和组件数量有限制；性能数值在实现前按目标设备和页面画像确定并测量。本阶段不添加生产依赖，实施时若需拖拽或编辑库，应先评估现有能力和依赖成本，再按项目约定确认。

## 风险与验收要求

| 风险 | 处理与验收 |
| --- | --- |
| 即时预览与终端不一致 | 相同配置分别检查后台、微信开发工具与真机；轮播、热区、横滑、长文本、图片失败逐项核对 |
| 新组件导致旧客户端白屏 | 运行时能力校验、未知组件受控兜底、旧配置兼容及历史回退测试 |
| 发布覆盖别人编辑 | 保留草稿和发布双修订检测；双会话测试冲突与恢复，不自动覆盖 |
| 素材或目标失效 | 保存、预览、发布重新校验；运行时也提供失效兜底，不让用户点入死链 |
| 页面复制残留原身份 | 复制后修改不影响来源页面，且不会自动成为主页或继承线上版本 |
| 商品价格库存过期 | 页面数据来自商品域，购物动作重新报价和查库存；停售、售罄、无匹配分类均有状态 |
| 营销状态错误 | 领取资格与结果由权益域判定；页面不得仅根据按钮状态判定成功 |
| 自由布局维护成本 | 默认使用固定模板；自由布局需独立产品与端适配验收 |

第一阶段验收应覆盖：新建专题→添加导航和商品→画热区→即时预览→保存草稿→服务端校验→授权发布→消费者打开→历史回退。同步覆盖只读、编辑、发布不同权限，未发布、空页面、失效素材、商品停售、异常重试、重复发布和版本冲突。目标是运营能独立完成这些步骤，具体耗时以代表性任务实测。

实现时按项目约定先写失败用例，再完成单元、契约集成和关键流程 E2E；JavaScript 修改后运行 npm test，记录覆盖率范围并达到项目要求。自动化通过后仍需浏览器 UAT、微信开发工具和目标真机验证。配置发布、代码部署、微信提审发布和生产验收分别记录。
