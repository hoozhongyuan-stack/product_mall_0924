# 产品介绍：B2C 商城与前置仓协同系统

核对日期：2026-10-15。阅读对象：产品负责人、经营人员、交付人员与新加入项目的开发者。本文解释当前分支的产品结构与业务边界；具体字段和权限以 [API 契约](contract-v1.md)为准，实施与验收证据沿用各模块文档。

## 产品定位

这是一个**平台统一经营、多个前置仓协同履约、餐饮店引入消费场景**的 B2C 微信商城。

平台统一维护商品、价格、页面和运营规则。顾客可以选择前置仓购买本地配送／自提商品，也可以购买平台快递商品和虚拟权益。餐饮店通过桌码提供固定店铺和餐桌的消费场景，由匹配的前置仓履约，并按成交时的佣金规则核算收益。

适合有平台运营团队、本地库存节点和线下合作场景的业务。当前代码支持通用实物与权益商品，仓库中的酒水示例用于业务体验，不代表系统仅能经营酒水。

产品边界是一个平台运营体系下的多仓和联盟协作，不能将它直接描述为任意商家自助入驻、独立定价、自建店铺的多租户 SaaS。现阶段也没有骑手 App、银行自动打款或已完成生产验收的承诺。

## 谁使用，分别负责什么

| 角色 | 使用位置 | 主要职责 | 关键边界 |
| --- | --- | --- | --- |
| 顾客 | 微信小程序 | 浏览、选店、购物、下单、付款报告、查询订单、收货、售后、会员权益 | 仅查看与操作自己的订单、地址和权益 |
| 平台运营与管理人员 | PC 管理后台 | 商品、价格、库存治理、订单资金、平台快递、售后、装修、营销、权限和发布 | 按操作权限授权；平台查看本地履约进度，备货和实际交接由仓端完成 |
| 前置仓员工 | 小程序 → 前置仓中心 | 本仓销售状态与库存、向平台进货、备货、配送、自提、授权权益核销、账户与提现 | 不修改平台商品价格；不操作其他仓，不承担平台快递发货 |
| 餐饮店员工 | 小程序 → 联盟中心 | 本店商品上下架、查看桌码来源订单、佣金与提现申请 | 不持有库存仓，不备货、不配送、不执行退款 |
| 部署及维护人员 | 服务器与受控后台 | 环境配置、镜像与迁移、备份恢复、任务健康和外部接入 | 技术部署不等于已开通支付或已正式发布小程序 |

前置仓中心、联盟中心与顾客中心在同一个小程序内共用会员身份。员工入口及可操作内容由所属关系和具体权限决定。

## 典型业务闭环

### 1. 普通顾客购买与履约

1. 顾客进入后台指定的首页微页面，定位或手动选择前置仓；拒绝定位时仍可手动选择。
2. 浏览分类、商品和规格，将商品加入当前场景的购物车。切换店铺不会把原购物车迁移到新店。
3. 确认订单时由服务端核对商品、库存、地址、交付方式、优惠及运费，并生成报价。
4. 提交订单后暂占库存；可信收款确认后扣销售库存。线下付款报告和上传凭证本身不等于已收款。
5. 配送和自提由指定前置仓交付；快递由平台总仓分批发货；虚拟权益由成交授权范围内的主体核销。
6. 交付、收货和核销不重复扣销售库存。订单是否完成按有效交付义务、权益及售后事实判断，部分交付不提前完成整单。

### 2. 餐饮桌码消费

1. 平台创建餐饮店、地址、餐桌和授权员工，按地址匹配可服务的前置仓。
2. 顾客扫描真实餐桌小程序码，进入固定餐饮店与餐桌的消费场景；顶部不提供自由切店。
3. 商品必须同时满足平台可售、履约仓销售授权和餐饮店上架条件。
4. 服务端保存店址、桌号与履约仓快照，不要求顾客填写个人收货地址；缺货时不静默换仓。
5. 前置仓完成配送。餐饮佣金根据成交快照核算，满足结算与售后条件后才能进入提现申请流程。

餐饮扫码会话具有身份、有效期和配置修订约束；普通链接不能代替有效扫码访问。[餐饮联盟实施说明](dining-alliance.md)记录了完整边界。

### 3. 前置仓向平台进货

前置仓员工选择有进货价格的规格并填写数量，核对后提交进货单。线下付款后选择、上传并提交凭证，由平台核款，再进入整单发货和整单验收。验收按独立增量入库记录处理，不覆盖现有余额或订单占用。

进货价格保存单据快照；付款、发货、验收等状态按权限和请求身份推进，重复请求不得重复入账。数量输入、选图生命周期、失败重试与编号规则见[进货及配送说明](procurement-delivery.md)。

## 必须理解的业务规则

### 库存与履约归属

| 交付类型 | 库存与操作主体 | 顾客看到的主要事实 |
| --- | --- | --- |
| 配送到家 | 指定前置仓库存，仓端备货、派送、异常恢复和交付 | 履约仓、配送状态、实际交付与剩余数量 |
| 到仓自提 | 指定前置仓库存，仓端核对自提凭证并交接 | 自提地址、凭证、待提与已提数量 |
| 快递 | 平台总仓库存，平台按可发数量分批发货 | 批次物流、每批数量及收货状态 |
| 虚拟权益 | 按商品配置冻结为仅平台、指定仓或两端共同授权 | 可核销范围、已用、冻结、剩余次数及实际核销方 |

购买入口的前置仓与实际履约仓不是同一概念。新快递订单的前置仓只作来源记录，不因此产生本地仓履约结算。共同授权权益使用同一份余次，两端核销不会各生成一份额度。

库存池按基础单位记账。同一物理库存的“瓶”“箱”等销售视图不能相加冒充库存；不同计量单位也不能直接求总量。下单预占、付款扣减、取消释放、退货回库通过统一库存入口处理。

售后仅冻结对应数量，其他可交付部分继续履约。未交付退款回原扣库仓；已交付商品需退货验收后按实际可售量回原仓；已使用权益退款不自动恢复使用次数。完整规则见[履约治理](fulfillment-governance.md)。

### 运费与费用承担

后台可配置运费、地区、配送围栏、时间、起送及包邮门槛。门槛按**商品金额减优惠券优惠**计算，不含运费，积分抵扣不改变门槛；先校验可配送条件，再判断包邮。

| 场景 | 顾客免付部分由谁承担 |
| --- | --- |
| 前置仓本地配送的经营包邮 | 履约前置仓 |
| 满足平台活动的本地配送包邮 | 平台；覆盖经营包邮，不能双方重复承担 |
| 平台快递的经营包邮或活动包邮 | 平台；新快递订单由平台总仓履约 |
| 到仓自提 | 自提不收运费 |

每笔订单冻结成本、顾客运费和补贴承担方，满足：

`配送成本 = 顾客运费 + 前置仓承担 + 平台承担`

费用修改不重算历史订单；顾客已支付的运费不能再次扣仓。平台活动可能使平台净收益为负，应在运营配置与资金核对中明确承担。旧版“快递沿用所选仓履约”及“所有包邮均扣仓”的描述已被本轮[履约治理](fulfillment-governance.md)覆盖。

### 收益、佣金与提现

平台分成比例针对商品利润计算，不能把“20%”直接乘整笔销售额。成本按销售规格单位和数量计算；成交时冻结成本、比例、优惠与运费承担快照，配置改变不重算历史收益。

无优惠、无运费、无售后时，商品实付 100 元、成本 60 元、平台利润比例 20%，则平台利润为 8 元，前置仓结算为 92 元。如果该餐饮场景商品佣金比例也是 20%，餐饮佣金为 8 元，从仓利润份额扣除，仓净结算为 84 元，满足 `100 = 8 + 8 + 84`。有运费、优惠、退款时按成交快照逐项分摊，不能直接套这个简例。

收益需满足可信收款、实际完成、超过成交售后期等条件。成本缺失、负利润、退款归属不明或历史快照不足时先冻结核对，不伪造可提现余额。前置仓提现包含申请、审核及线下付款事实登记；餐饮提现目前为申请与审核，不执行资金打款。后台登记付款也不等于系统调用银行完成转账。

### 状态、权限和重复提交

保存草稿、发布页面、上传代码、设为体验版和正式发布是不同操作。上传凭证与核实到账、审核通过与实际打款也分别记录。

订单、资金和库存等写入由服务端核对实时权限、归属、修订与请求身份。普通后台业务操作不重复要求输入操作员密码，但保留登录、授权、审计、并发及幂等控制；退款等流程仍有对应的经办与复核边界。网络结果未知时先查原操作，不直接换请求重复执行。

业务展示编号采用类型前缀、北京时间和流水，例如 `JH + YYYYMMDDHHmmss + 六位序号`；XS／CY／JH／JF／SH／TK 分别代表普通销售、餐饮销售、进货、积分兑换、售后及退款。内部 UUID 与支付渠道交易号独立保留。

## 交接与验收建议

新接手团队可按以下顺序体验产品：

1. 建立平台主账号与权限组，配置外部接入及人员职责。
2. 建立平台总仓与前置仓，维护商品、规格、价格、成本、销售授权和实际库存。
3. 配置并试算快递模板、本地配送围栏、起送和包邮政策，确认费用承担。
4. 发布微页面，设为首页并发布底部导航，检查分类图、店铺切换和餐饮固定场景。
5. 使用明确标识的测试数据分别走通配送、自提、分批快递、各授权范围权益及混合订单。
6. 验证付款核对、部分交付、售后冻结、退货回库、收益与提现权限；真实渠道结果单独留证。
7. 核对服务器 SHA、源码包摘要、微信开发／体验版本，并在真机上验证冷启动、定位、输入、上传和弱网重试。
8. 完成配对备份与隔离恢复演练，核对数据、媒体和凭据可恢复性后再作生产上线判断。
