# 餐饮联盟实施说明

状态：本地开发及验证已完成，尚未部署。对应用户已确认的餐饮联盟 HTML 交互稿；本文件不表示已部署或微信真机验收。

## 业务边界

餐饮店是独立消费场景与佣金归属主体，不创建库存仓，不参与备货、配送、库存写入或退款执行。后台创建餐饮店、维护地址坐标、联系人、餐桌编号以及管理人员。人员使用既有会员身份，分商品、订单、财务权限。餐饮店不会进入公开定位前置仓列表。

创建或修改餐饮店时按店址坐标选择配送范围内最近的启用前置仓；没有可服务仓明确拒绝。一次扫码固定履约仓，缺货、仓停用、配置变化均拒绝继续，不静默换仓。商品必须同时满足平台可售、前置仓销售授权和餐饮店上架条件；库存读取原仓物理库存及既有预占规则。

餐桌编号在同店唯一，不同店允许相同编号。真实小程序码进入 `pages/dining/shop`，携带私有餐桌编码。扫码会话绑定当前会员、餐饮店、餐桌和前置仓修订，最长两小时；停用、改号或改店址使旧会话失效。前端不持久保存访问凭证，退出购买闭环或小程序进入后台清理访问；重新进入需要扫码。直接页面链接不会展示店铺。

报价和下单只接受扫码会话编号，不接受客户端指定仓库、个人地址或交付方式。服务端生成餐饮店地址、联系人和桌号快照，履约复用原仓配送订单。历史订单保留成交目的地，公开订单响应不暴露扫码会话凭证。

## 佣金与提现

商品佣金比例是商品级统一规则，所有餐饮店共用，按万分比保存。成本先读实际履约仓的 SKU 成本覆盖；无覆盖时读现有全仓默认进货成本，并明确标记来源。销售单位变化需重新配置，不把旧单位成本套给新单位。

每项佣金 = floor((该项商品成交实付分 - 该项进货单价分 × 成交数量) × 商品佣金万分比 / 10000)。商品成交实付沿用现有优惠分摊，运费单独展示，不增加商品利润。订单提交时冻结数量、单位版本、实付、成本来源及规则修订；数据库限制改写成交快照，后续配置不重算历史订单。

订单未完成展示预计佣金；可信收款且真实履约完成后显示已入账待过售后期；严格超过该订单既有售后期限才允许提现申请。缺成本、缺比例、负利润或存在未撤销/未驳回的售后退款时冻结，等待明确业务规则，不自动编造退款后佣金算法。

提现使用本人权限、金额校验、防重复请求键与锁，申请占用可用余额，后台审核再次核对售后状态，通过审核仍保留占用，驳回释放。本期不执行资金打款。用户已确认餐饮佣金从履约前置仓利润份额中扣除：平台原利润计算不变，仓原结算减餐饮佣金，成本使用同一履约仓成交快照。扣后须覆盖进货本金，否则双方该订单未结算资金冻结；餐饮佣金不能在仓净结算及扣除事实入账前变为可提现。订单冻结 `FULFILLMENT_STORE_PROFIT` 承担方，旧订单不补写旧快照，已结算收入不追改。收款资料、实际打款与退款后的最终资金追偿须确认规则后接入。

## 对外契约

后台权限：`dining.read`、`dining.manage`、`dining.finance.read`、`dining.finance.manage`。后台 Cookie 写入需 CSRF；小程序接口需会员 Bearer，并实时校验所属餐饮店及具体能力；独立财务读取权限允许读取选店列表，不授权读取桌码和人员；接口复用数据库限流，响应禁止缓存。

后台统一前缀 `/api/v1/admin/dining-alliance`：

- `GET/POST /restaurants` 与 `GET/PATCH /restaurants/{id}`：餐饮店创建、匹配仓、修订更新；创建必填 UUID `requestKey`，同键同内容返回原店，同键异内容409，修改提交 `revision`。
- `GET/POST /restaurants/{id}/tables` 与 `PATCH /restaurants/{id}/tables/{tableId}`：餐桌建立、桌号与启用状态维护。
- `GET /restaurants/{id}/tables/{tableId}/code`：真实微信小程序码 PNG/JPEG，按实际格式返回 Content-Type 和 .png/.jpg 下载名，失败返回明确错误，不生成示意码。
- `GET/POST /restaurants/{id}/staff`：会员员工绑定及商品、订单、财务能力维护；新增 `revision=0`，修改使用读取的最新修订，旧草稿409。
- `GET/PATCH/PUT /product-ratios`：商品统一佣金比例与修订。
- `GET/PUT /purchase-costs`：对应仓 SKU 的进货成本覆盖与单位版本。
- `GET /orders`、`GET /orders/{orderId}`：餐饮来源订单及地址、桌号、原仓履约事实。
- `GET /restaurants/{id}/account`、`GET /restaurants/{id}/withdrawals` 与 `POST /restaurants/{id}/withdrawals/{withdrawalId}/{approve|reject}`：账户与提现审核。

小程序统一前缀 `/api/v1/app/dining-alliance`：

- `GET /restaurants`：仅本人管理的餐饮店，不能作为顾客公开目录。
- `POST /scan`：`tableCode` 换取当前会员的临时扫码会话。
- `GET /sessions/{sessionId}/products`、`DELETE /sessions/{sessionId}`：当前扫码可售列表、结束访问。
- `GET/PATCH /restaurants/{id}/products`：上下架；不提供库存编辑。
- `GET /restaurants/{id}/orders`、`GET /restaurants/{id}/orders/{orderId}`：餐饮订单，不提供履约写入口。
- `GET /restaurants/{id}/account`、`GET/POST /restaurants/{id}/withdrawals`：读取佣金与本人提现申请。

既有 `POST /api/v1/app/checkout/quotes` 增加互斥 `diningSessionId`；响应 `dining` 和 `addressRequired=false`。`POST /api/v1/app/orders` 仍沿用报价编号和既有防重复键，服务端重验扫码、上架和原仓库存。餐饮端订单 DTO 使用顶层 `address/tableNumber/lines`，普通订单 `dining` 仅包含目的地信息。

## 工程评审

1. 独立 `backend/dining_alliance` 持有餐饮、桌码、人员、成本覆盖、比例及佣金快照；checkout 只读会话，orders 统一协调库存、支付和快照。无新增生产依赖。
2. 数据库保证同店桌号唯一、商品比例唯一、仓 SKU 成本唯一、防重复提现及不可变成交快照。
3. 修改配置使用修订号；下单重验实时权限及库存；提交/提现未知结果保留原请求重试。审核锁定相关订单，售后与提现不会同时绕过状态校验。
4. 列表显式分页；余额计算完整数据，佣金及提现明细显示最近100条。顾客可售集合过滤后分页，不能只过滤仓商品首屏。
5. 验证证据在本节最终追加。真实微信码依赖对应小程序版本发布及凭据配置，不以网络 mock 替代验收。
6. 后续退款重算、提现打款在餐饮财务域扩展，原订单和库存域事务仍通过既有命名入口。仓净收入与餐饮佣金由支付结算和餐饮财务共同核对，不额外创建第二笔仓扣款流水。
7. PC 沿用 Element Plus、既有框架与商城红变量；小程序原生组件，居中标题、独立餐饮购物篮与结算页，错误、空态、无权限和修订冲突有明确反馈。桌面及390px浏览器、小程序自动化和真机分别记录。

## 仓利润承担餐饮佣金（2026-10-11 追加确认）

无运费示例：实付100元、履约仓进货成本60元、平台利润比例20%、餐饮商品佣金比例20%。利润40元，平台8元，餐饮佣金8元，前置仓结算84元（60元成本加24元净利润）。100 = 8 + 8 + 84。每笔仓钱包仅净入账一次，不先加92再重复减8。实际运费和优惠继续沿用原订单快照与整数分分摊。

新订单中的仓财务与餐饮佣金共用实际履约仓成本，配置变更不重算。旧餐饮快照未冻结承担方时展示冻结待核对；不会把新规则追扣已结算仓钱包。餐饮可提现要求订单完成且过售后期、无相关售后退款，以及可信的仓收入已结算并记录同额餐饮佣金扣除。

前置仓收入读接口新增 `beforeDiningFen`（扣餐饮佣金前结算）和 `diningCommissionFen`（餐饮佣金扣除），已有 `storeFen` 改为餐饮订单的扣后净结算。普通订单扣除为0，不改变原分润。HELD金额输出null，不能呈现为确定的0元或可用余额。PC及小程序同时展示扣前、扣除和扣后金额，直接使用服务端净额，不在客户端再扣一次。餐饮资金由原结算扫描命令统一处理，账户读取不写资金事实。

## 餐桌码目标版本配置

生成接口将部署配置明确传给微信 `getwxacodeunlimit`，不按 DEBUG、域名或客户端请求自动判断目标版本。生产默认 `DINING_CODE_ENV_VERSION=release`、`DINING_CODE_CHECK_PATH=1`：打开正式版并检查餐饮页面已发布。UAT 必须显式设置：

```dotenv
DINING_CODE_ENV_VERSION=trial
DINING_CODE_CHECK_PATH=0
```

这会打开体验版并允许餐饮页面尚未正式发布。仍需已上传包含 `pages/dining/shop` 的小程序代码，并在微信平台选择对应体验版本；取消路径检查不会创建缺失页面，也不代表扫码访问已经验收。`DINING_CODE_ENV_VERSION` 只接受 `release`、`trial`、`develop`，`DINING_CODE_CHECK_PATH` 只接受 `1`、`0`；非法部署值会阻止服务启动，运行时非法覆盖也会在访问微信凭据及码服务之前返回配置错误。生产 Compose 的 `x-backend-env` 已显式透传这两个环境变量，release/web/维护任务共用同一配置；UAT 私有 release.env 必须设置上述值。修改环境变量后须重新创建应用容器以加载配置，重新生成并扫描对应桌码核对实际版本。

配置测试覆盖正式版默认、体验版关闭发布页面校验、开发版显式选择、非法配置先于网络拒绝及启动环境变量校验；测试模拟微信 PNG/JPEG 响应，包含可解码的二进制图片 fixture，以及截断、异常结束、JSON 错误和超限数据拒绝；不代表真实微信二维码生成或扫码成功。
