## 1. 交易并发用例与事务边界

测试使用真实 PostgreSQL、独立数据库连接和并发屏障，分别控制事务 A 先提交、事务 B 先提交、外部响应超时后重试。不能把两个顺序请求、SQLite 模拟，或仅界面按钮禁用当作并发证明。每例保存用例编号、数据库版本、隔离级别、请求键、订单/订单项/流水 ID、事务开始与提交时刻、最终行快照、关联日志和通过结论。阶段 B 实现锁库与下单时先落地 C01—C05、C09—C10；阶段 C 实现收款时落地 C06—C08 及无效通知用例。真实微信验签、关单和资金结果另按实施待验证清单 T-02 验证。

| ID | 初始数据与并发动作 | 必须满足的结果 |
|---|---|---|
| C01 多 SKU 部分不足 | SKU A、B 各有余额；同单需要 A 1、B 2，但 B 只可售 1。提交过程中检查 A 已尝试占用后出现 B 不足。 | 整单失败；无有效订单、占用、权益冻结或残留 A 锁定；余额及流水与初始值一致。改为 B 1 后全单原子成功。 |
| C02 热点 SKU 超卖 | A 可售 1；两个不同用户同时各下单 1，双连接在读取前对齐。 | 恰好一个订单占用成功；另一个明确库存不足；`reserved <= on_hand`，可售非负，无重复有效占用。互换事务先后重复测试。 |
| C03 反向多 SKU 锁序 | 两单分别以 A→B、B→A 的客户端顺序申请同仓相同 SKU，余额可供两单。 | 服务端统一按 `(warehouse_id, sku_id)` 排序取锁；两单最终可完成，无死锁；若出现数据库死锁只能按有界次数重试整个事务，不产生半单。 |
| C04 下单幂等与未知结果 | 同一用户用同一键/同一请求并发提交，并模拟第一次提交成功但 HTTP 响应丢失；再用相同键/不同内容提交。 | 相同内容只产生一单及一组占用，重试返回原结果；不同内容返回稳定冲突码。唯一键由数据库强制，不依赖进程内锁。 |
| C05 券与积分争用 | 同一券及可用积分恰好只够一单；两个订单并发占用，分别尝试先拿券和先拿积分。 | 最多一单成功；失败单无库存或权益残留。可用积分 = 总余额减所有有效冻结，检查与冻结写入必须在同一锁保护下完成。 |
| C06 重复及乱序支付通知 | 待付款订单收到同一微信成功通知两次、不同事件 ID 的同笔成功通知，且处理顺序可反转。 | 仅一次 `PENDING→PAID`、库存正式扣减、券核销、积分扣除和资金流水；事件记录可去重追踪；重放返回幂等结果。 |
| C07 收款与超时关单竞态 | 同一待付款订单，支付成功确认和超时任务同时尝试提交；分别令任一方先拿订单锁。 | 只能形成 `PAID` 或 `CLOSED` 的一个已提交状态。`PAID` 时权益结算一次；`CLOSED` 时占用释放一次，后来的真实成功款项记异常，不恢复原单。 |
| C08 迟到账与线下确认 | 已关闭订单再收到真实成功通知，或后台线下确认与关闭竞争；另外提交金额不符确认。 | 迟到账建唯一异常记录并待核对/退款；关闭单不进入履约。线下确认仅授权人员且实收金额匹配时生效一次；金额不符拒绝并记失败审计。 |
| C09 零元订单 | 优惠后应付 0 的订单与相同幂等键重试并发；预支付/通知入口也尝试作用于该单。 | 创建事务内直接 `PAID` 并一次性结算库存、券、积分；不生成有效支付尝试、不调用支付渠道；重试仍是一单。 |
| C10 时限快照与重试 | 两笔订单创建于不同的支付时限配置版本；修改当前配置后同时扫描超时，并使任务中途失败后重试。 | 各单只使用创建时保存的到期时刻；未到期单不关；已到期单只释放一次；重试按状态幂等。 |
| C11 无效通知 | 签名错误、商户号/订单号不匹配、金额不匹配的通知分别到达；与合法通知竞争。 | 无效通知不改变订单、库存、权益或资金流水；保存去敏的拒绝原因与关联追踪；合法通知仍能按状态机处理。 |

数据库不变量：`inventory_balance` 按 `(warehouse_id, sku_id)` 唯一，`on_hand_base_units >= 0`、`0 <= reserved_base_units <= on_hand_base_units`；可售量为两者之差。订单项每仓最多一个有效占用。订单收款状态、库存占用状态、券/积分状态和流水数量必须可相互核对。资金外部请求不持有数据库事务；回调先验签、解密并核对商户号、订单号和金额，随后在短事务内抢占状态转换。成功审计与业务状态同事务写入，失败审计单独持久化。

上述三处交易实现细节已在 [B0 交易实现契约](contract-v1.md#51-b0-交易实现契约失败重试迟到账与积分冻结)定稿：失败事务不占用幂等键、成功键的 24 小时结果重放与订单存续期防重用；以唯一资金身份登记迟到账并由资金交易域负责查单、异常与退款；每会员积分账户行锁保护冻结。此处仅解除**设计细节未定稿**的开工障碍。C01—C11、真实支付验签及资金结果仍待对应阶段实施验证，不得写作已通过。

### B0 契约评审记录（2026-09-25）

本次只调整现有研发契约与评审记录，没有迁移、接口、页面或运行结果。实施时不得把以下设计结论代替数据库与并发证据。

1. **模块与契约：** 阶段 B 的 `orders` 协调整单锁库、券/积分占用和下单幂等；`inventory` 拥有仓库、余额、占用与流水；积分账户由会员权益域提供原子冻结接口。阶段 C 的 `payments` 拥有资金收据、迟到账异常、查询补偿与退款状态，订单模块提供关闭状态，跨模块只经明确业务入口调用。
2. **数据库规则：** 订单成功键 `(actor,scope,key)` 唯一且随关联订单保留；资金收据 `(channel,merchant_account_id,external_trade_no)` 唯一，异常 `receipt_id` 唯一；积分账户 `member_id` 唯一、冻结总量非负，同订单有效冻结唯一。库存余额与占用的不变量仍按本节数据库不变量执行，具体约束由迁移和 PostgreSQL 回退验证。
3. **重复、并发与失败：** 下单同键经事务级锁串行，失败全回滚且允许原请求重试；成功后同内容重放一单，不同内容冲突，结果缓存过期后拒绝复用键。迟到通知按外部交易身份去重、查单补偿，不恢复关闭订单；积分冻结在会员账户行锁下检查和写入。C01—C11 是后续验收门槛，尚无实测结果。
4. **数据量与查询：** 幂等按键等值查找、资金收据按渠道交易号等值查找、积分账户按会员 ID 锁一行；异常队列按状态及创建时间分页。响应缓存 24 小时后可清理，但成功键墓碑与订单保持关联。实现切片需用实际索引、查询计划和热点 SKU/积分账户等待时间复核。
5. **权限与证据：** B0 为文档评审，无权限测试或业务功能通过结论。阶段 B 需验证库存权限、整单失败回滚、重复提交与积分争用；阶段 C 需验证迟到账查询补偿、`payment.anomaly.resolve`/`refund.initiate` 与 `refund.confirm` 分权、线下退款不同账号确认和资金状态，实际微信商户联调另记录。
6. **项目扩展点：** 幂等和订单状态由订单域扩展；库存余额及流水由库存域扩展；积分过期批次、冻结和流水由会员权益域扩展；资金异常及退款由资金交易域扩展。不得在 PC 页面或小程序本地复制这些判定。
7. **组件与页面规则：** B0 未修改页面或引入组件。后续库存、订单与异常处理页面沿用现有设计变量，以及加载、空、错误、无权限和窄屏状态；对高影响库存与资金操作按高保真样板和工程规则增加确认与结果反馈。具体页号、桌面/窄屏/模拟器或真机核对结果在对应开发切片记录。

## 2. 阶段 A 权限评审

项目确认：以上作为阶段 A 默认预设组，后续可由主账号调整。菜单可见性由对应的读取权限派生，不单独授予可绕过操作权限的菜单码。订单售后与库存管理在阶段 A 可以登录并看到无权限状态，其业务权限到对应阶段再授予。商品运营不能借 `catalog.write` 改价格、上下架或单位；商品创建时含 SKU 初始价、上架状态和单位的复合提交，服务端必须同时要求对应的 SKU 价格、状态和单位写权限，避免绕过单项接口。会员营销只能编辑草稿，不能发布。素材用途和引用仍须服务端校验；删除如未交付，不开放接口。

| 安全控制 | 阶段 A 可检查的结论 |
|---|---|
| 主账号初始化 | 仅管理命令在空库建立唯一 `OWNER`；交互输入初始凭据，禁止代码默认密码和明文日志。重跑初始化不额外产生主账号。交接人需指定。 |
| 会话与登录 | 服务端会话、HttpOnly Cookie、CSRF；本机同源 HTTP 仅用于开发，正式 HTTPS 时 `Secure` 必开。空闲 30 分钟失效；连续失败 5 次锁定 15 分钟并限制来源频率。 |
| 权限变更生效 | 账号停用、分组或组权限变更在事务内提升受影响账号 `auth_version`，旧会话下一请求失效或即时重算；不能仅依赖登录时返回的权限列表。 |
| 二次确认 | 页面、启动配置发布以及账号/权限高影响变更使用短期单次确认凭证，绑定操作者、动作、对象和修订号；执行时重新验证会话、权限、凭证与修订号。 |
| 审计 | 成功业务变更和成功审计同事务；拒绝/失败事件另行持久化，避免回滚抹掉失败记录。审计记录操作者、动作、对象、前后值摘要、结果、请求号和时间，凭据脱敏。 |

最小权限测试：每个操作码用有权账号、无权账号、已停用账号各测允许/403/401；复合商品创建缺 `sku.price.write`、`sku.status.write` 或 `sku.unit.write` 时逐项拒绝；越权直接调用 API 与跨账号修改拒绝；会员营销编辑后发布拒绝；主账号唯一、子账号不能编辑 `OWNER`；修改组权限后旧会话无效；过期 `expectedRevision` 返回 409；二次确认凭证重放/跨对象使用拒绝；失败审计可查且不泄密。阶段 A 只验证本阶段账号和页面发布权限，不能把代码版本发布或资金权限写成已通过。

权限设计评审结论：与需求文档第 3.8、12.1、13.12 节对照后，阶段 A 的默认组、操作粒度、主账号边界、会话失效与审计路径在方案层面可通过；复合商品接口和草稿/发布分离已纳入必须测试的绕权用例。默认组已获项目确认。此段记录的是当时的**设计评审**；账号权限的实现验证见第 5 节，完整渗透验证及后续商品、页面权限验收仍未发生。

## 3. 本机部署方案与验证

本机拓扑：微信原生小程序开发工具/目标手机与 PC Vite 开发服务访问 Django `/api/v1`；Django 连接本机 Docker Compose PostgreSQL；商品素材落在仓库外或忽略的持久化 `media/`。PC 开发代理已将 `/api` 转到 Django；生产同源、HTTPS、持久化存储和反向代理在目标环境确定后再定。Compose 只管理数据库，Django 与 Vite 由本机开发命令启动；小程序当前只有骨架，尚未真机运行。

配置位于仓库根目录的 `compose.yaml`、`.env.example`。数据库镜像已固定为 PostgreSQL 18.6 及其摘要，端口 `127.0.0.1:15432`（可通过 `.env` 改），仅本机访问；Docker secret 文件位于被 Git 忽略的 `secrets/postgres_password`，数据卷 `pgdata` 挂到 PostgreSQL 18 的 `/var/lib/postgresql`，健康检查通过 `pg_isready`。不在文档、Git 或终端回显密码。

后续阶段 A 的本机流程：确定并锁定 Python/Django 与 pnpm 依赖版本 → 初始化 Django/Vue/小程序工程 → 定义开发配置和媒体目录 → 生成并评审首批迁移 → 空库迁移、重跑迁移与回退演练 → 建立唯一主账号 → 跑服务端权限测试与页面读写冒烟。迁移由应用命令执行，不在数据库容器启动时自动执行。启动顺序要等待数据库健康而非仅等待容器启动；备份/恢复用独立演练库验证后记录耗时。`docker compose down -v` 会删除数据卷，不作为日常停止命令。
