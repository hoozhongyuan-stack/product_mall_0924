# 研发工程与页面规则

状态：2026-09-25 起用于后续研发切片。本文规定工程边界、依赖、组件和页面检查方法；业务规则以工作区《B2C商城小程序V1.0需求文档.md》为准，接口字段以[数据与 API 契约](contract-v1.md)为准，视觉以工作区《B2C商城小程序V1.0_高保真视觉样板.html》为参考。样板中的示例数据、未开发能力不能直接当作已交付功能。

## 1. 模块与目录职责

| 位置 | 职责 | 调用边界 |
| --- | --- | --- |
| `backend/config/` | Django 配置、URL 装配和部署入口 | 不放商品、页面等业务规则。 |
| `backend/accounts/` | 后台账号、权限、会话、确认凭证和审计 | 其他模块通过公开的鉴权/审计入口使用，不直接改账号或权限表。 |
| `backend/catalog/` | 分类、商品、SKU、素材及其公开展示条件 | `pages` 等模块需要商品状态时，通过明确的只读查询或业务入口获取；不在本模块操作页面发布表。 |
| `backend/inventory/` | 仓库、余额、入出库、盘点审核及不可改写流水 | 经 `catalog/inventory_access.py` 读取 SKU 与当前单位；向商品模块仅暴露 `inventory/sku_guards.py` 的历史引用检查。其他模块不得直接改余额或写流水。 |
| `backend/customers/` | 小程序会员身份、微信登录令牌、收货地址、有效消费与等级运营读模型 | 其他域通过 `customers.auth.resolve_member` 与 `customers.addresses.member_owns_active_address` 校验，不直接读写令牌或地址表。D4运营通过安全分页读模型查询会员，通过benefits公开规则入口配置，不暴露微信身份。 |
| `backend/shipping/` | 首版固定运费配置、修订号和配送费计算 | `checkout` 报价与 `orders` 提交通过 `shipping.service` 读取；后台写入须 `settlement.shipping.manage`，不在客户端自行计算运费。 |
| `backend/benefits/` | 会员券、活动与发行凭证、积分批次及权益暂占、释放、核销流水 | `checkout` 只读取可用权益和试算；`orders` 在整单事务内调用命名入口。D4通过修订规则入口配置积分与等级参数；D4.1通过活动／发放命名入口管理永久额度、本人领取与恢复凭证，账号权限与商品选择沿所属域公共接口。手工积分调整界面留后续切片。 |
| `backend/checkout/` | 商品选购报价快照与当前价格/库存核对 | 经 `customers` 校验身份与地址，经 `inventory/availability.py` 读取可售量，经 `catalog` 只读 SKU/价格，经 `shipping` 与 `benefits` 计算金额；不改余额或权益，不承载订单事务。 |
| `backend/points_exchange/` | 独立积分售价、兑换上下架、报价与兑换事务及恢复凭证 | 经 `catalog/exchange_access.py` 获取可用商品快照，经 `customers` 重验本人身份与地址；复用 `orders`、`inventory`、`benefits` 命名入口一次扣积分和库存。独立闸门默认关闭；履约和售后使用共同入口，不生成现金收退款凭证。 |
| `backend/orders/` | 订单提交、成交快照、防重复键、取消、超时关闭及统一已付款转换 | 读取 `checkout` 报价并重验 `catalog`、`shipping`、`benefits`；经 `inventory/reservations.py` 锁定、释放或结算库存。订单域不直接改余额。真实收款方式与对应页面完成验证前，公开提交按方式关闭。 |
| `backend/payments/` | 付款说明与时限、用户报告、授权核对、可信到账凭证、通知去重及异常历史；按方式开放能力 | 凭证先持久化，结算时先锁订单，通过 `orders.service` 的统一入口结算；不直接改库存或权益。`availability` 为提交、报价和商品展示提供一致的方式闸门。C1 核对意图不可改写，首次确认需当前权限与密码二次确认；用户报告不代表资金。C2 适配器拥有 RSA 签名/验签、AES-GCM 解密、预支付及查关单；网络调用在业务事务外，支付尝试与操作租约先持久化，可信到账接入共同资金入口。人工资金处置和真实商户验收留后续。 |
| `backend/notifications/` | E2 订阅消息的候选事件、模板与授权证据、持久化任务、尝试和恢复状态 | 业务域只在事实提交事务内调用 `record_event`；通知域不修改订单、履约或退款事实。渠道调用须在数据库事务外；E2.0 默认关闭且只提供显式合成验证，不代表微信平台接收或用户送达。 |
| `backend/fulfillment/` | C3 已付款订单发货、收货、核销凭证与操作历史 | 只在 `orders` 的已付款事实后履约，发货／核销不再次扣库存；凭证码和二维码只经本人订单响应返回，PC 用输入码查验而不读取订单详情中的明文。物流轨迹适配不得改写发货事实。 |
| `backend/aftersales/` | 售后期限快照、订单项申请、审核/撤销、数量与商品退款金额占用、处理事件 | 先锁订单，使用订单项成交实付快照与 `payments.access.applied_receipt`；向履约提供守卫和批量摘要。退款最终确认由 `payments.refunds` 协调，通过 `inventory.refunds` 和 `fulfillment` 公共入口写副作用，再完成售后；不直接改余额、核销计数或发起第三方请求。 |
| `backend/pages/` | 页面草稿、预览、发布、版本和页面组件配置 | 引用商品或素材时调用对应模块的校验/读取入口；页面发布事务由本模块负责。 |
| `pc-admin/src/App.vue`、`router.ts`、`api.ts` | 登录后的应用框架、路由、统一 HTTP 与会话处理 | 不沉积商品或页面的业务表单逻辑。新增跨模块公共能力有稳定复用场景后再拆到 `shared/`。 |
| `pc-admin/src/views/<业务域>/` | 业务页面、域内组件、类型和页面状态 | 通过统一 `api.ts` 访问服务端；不能以按钮隐藏替代服务端权限检查。域内实现不从另一业务域的 `views/` 深层导入。 |
| `mini-program/pages/` | 原生页面布局、页面状态和导航 | 不直接拼装重复的请求/数据转换规则。 |
| `mini-program/lib/` | 请求封装与可独立测试的数据转换 | 不操作具体页面节点；后续稳定复用的原生 UI 放 `mini-program/components/`。 |

新模块先写明其负责的数据、业务操作与对外契约，再建目录。跨模块读写应有命名明确的入口；涉及多个模块的事务由发起业务操作的一方协调，避免双向依赖。当前 `catalog/views.py` 和 `ProductManagement.vue` 已承担较多职责，后续修改相关功能时按操作拆分，不为目录整齐做一次性重构。

现存待收敛的跨域依赖：业务视图引用 `accounts.views.method`；页面与商品模块仍需通过命名明确的只读入口交换目标与素材状态。独立微页面切片已将原先 `pages` 对 `catalog` 模型/媒体内部函数的直接读取收敛到 `catalog/page_targets.py`，将 `catalog/media_views.py` 对页面素材表的直接读取收敛到 `pages/media_access.py`；PC 两域共用的 `Asset` DTO 移到 `pc-admin/src/shared/media.ts`。下次触及剩余跨域调用时继续提取带测试的接口，不为修目录而改变现有业务行为。

## 2. 依赖与组件规则

- 当前技术选型维持 Django/PostgreSQL、Vue 3/TypeScript/Vite/Element Plus、微信原生小程序。Python 的直接依赖与锁定结果分别见 `backend/requirements.txt`、`backend/requirements.lock`；PC 依赖与锁定结果见 `pc-admin/package.json`、`pc-admin/pnpm-lock.yaml`。安装和升级时保持声明、锁文件与运行环境一致。
- 新依赖先说明：解决什么现有工具不能妥善解决的问题、运行时还是开发时依赖、维护和安全状态、包体/启动成本、移除成本；新增生产依赖先取得确认。不要为未来可能出现的需求预装状态库、请求库、UI 库或任务队列。
- PC 基础控件统一优先使用 Element Plus 的按钮、输入、选择、对话框、反馈等现有能力；项目样式通过语义设计变量配置，不在每页重写整套控件。业务特有的商品媒体、SKU、权限选择等保留在业务域。
- PC 组件分为三级：库控件；项目通用的页面标题、加载/空/错误状态、危险操作确认等；业务域内组件。相同语义和交互在至少两个页面稳定重复，或单页复杂度已影响维护时才提取。组件必须有清晰输入、事件、禁用/加载/错误行为；避免接收大量模式开关的“万能组件”。
- 小程序使用原生组件。商品卡、价格、媒体回退、页面状态等在稳定复用时提取原生自定义组件。PC 与小程序共享语义、业务状态、API 契约和视觉变量的定义，不共享 Vue 组件或 DOM 代码。
- 跨页状态确有需要时再评估 Pinia；服务器业务状态以接口响应为准，不靠前端缓存作权限或库存判断。

## 3. 设计变量与页面规范

以下是**后续新页面和触及页面的目标变量**，不是宣称现有 CSS/WXSS 已全部迁移。PC 建议映射为 `--mall-*` CSS 变量，并将需要统一的 Element Plus 主题变量映射到这些语义值。小程序保留同名语义清单，在确认目标微信版本的样式能力后选择 WXSS 实现；不可直接复制 PC 的像素尺寸。

| 语义变量 | 初始值 | 使用范围 |
| --- | --- | --- |
| `color-brand` | `#24583D` | 主操作、选中、关键链接 |
| `color-text` | `#243329` | 主要正文 |
| `color-muted` | `#607466` | 次要说明；用在浅底色上须检查对比度 |
| `color-danger` | `#B42318` | 破坏性操作和错误 |
| `color-price` | `#A03927` | 商品价格，不能代替错误色 |
| `color-surface` | `#FFFFFF` | 卡片和表单表面 |
| `color-canvas-admin` / `color-canvas-shop` | `#F4F6F1` / `#F7F7F2` | 后台与商城背景的有意差异 |
| `color-border` / `color-focus` | `#DCE6DD` / `#328055` | 边界和可见焦点 |

间距优先使用 4、8、12、16、24、32 的递进尺度；PC 以 px 落地，小程序以 rpx 和实际设备验证。圆角按小控件、卡片、强调容器三个语义层级选用，不因页面不同任意增加新值。字体至少区分页面标题、分组标题、正文、辅助说明；价格使用独立强调样式。当前已有近似但不完全一致的绿色、文字色和按钮样式，后续触及页面时逐步映射，避免一次性替换引入视觉回归。页面发布配置中的三项运营主题色是业务数据，不等同于后台/小程序的工程设计变量。

每个新页面或重要改版均按同一清单验收：正常内容；首次加载和重复提交中；数据为空及筛选无结果；网络/校验/服务端错误与重试；无权限或目标不可查看；窄屏、长文本和较大字号；危险操作确认与离开未保存表单；键盘焦点、标签和必要的状态播报。按高保真样板核对布局、内容层级和关键交互；样板没有展示的状态也要设计。PC 至少检查常用桌面宽度和约 390 px 窄屏；小程序至少检查开发者工具目标机型，真机结果单独记录。

## 5. 后续切片评审记录格式

每个切片在实施记录中简要回答，若不适用写明原因：

1. 归哪个模块负责；改变了哪些对外契约？
2. 哪些业务规则由数据库约束保证？
3. 重复请求、并发修改、中途失败分别会怎样？
4. 数据量扩大后，查询次数、分页、索引和返回体是否合理？
5. 允许、拒绝、错误和关键路径有哪些自动化测试与实测证据？
6. 新项目需要改变该能力时，应在什么位置扩展？
7. 沿用了哪些既有组件、设计变量和页面状态规则；例外是什么、为什么？

变更涉及页面时附上对应高保真样板编号、桌面/窄屏或模拟器/真机的实际核对范围。测试、视觉检查、模拟器和真机分别写结果，不能互相代替。
