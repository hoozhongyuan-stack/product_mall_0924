# 后台免密码操作与订单操作弹窗

实施范围：用户确认的后台免操作员密码、订单列表操作弹窗。此记录对应本地开发版本，提交、部署与真实支付渠道验收分别记录，不由本地测试推定。

## 入口与行为

统一订单列表、餐饮联盟订单列表和订单详情复用 `OrderActionDialog`。打开时读取最新订单，按当前账号权限、支付方式和履约状态提供确认收款、查询微信支付结果、确认备货、开始配送、确认送达、自提、快递发货、更正运单、查看物流、核销和售后入口。订单详情保留收款与履约事实；联盟订单保留餐饮店、桌号、地址、履约前置仓与仓库归属。

后台业务写操作不再填写操作员密码，也不再依赖 `X-Action-Confirmation`。后台登录、新账号密码、新密码与重复确认，以及微信商户密钥、上传密钥等业务凭据继续按原规则处理。修改本人密码和主账号重置子账号密码只提交新密码；实时权限、会话版本、CSRF、修订锁、操作日志、双人操作约束与幂等规则继续执行。

## 业务边界

- 确认收款保留实际账户、到账流水、金额、时间和核对备注；先持久化不可变核对记录，再确认结算。关闭订单的额外到账登记为异常资金，不恢复原订单。
- 微信查询调用已有支付查询服务，支付成功只由可信服务端凭证进入结算。查询接口不能人工把未付款改成已付款；本地测试不代表真实微信支付验收。
- 前置仓配送复用原状态机：备货、开始配送、完成配送。自提核验顾客凭证后交付整单剩余实物数量。部分数量核销仅用于核销商品。
- 已退款商品数量不再交付；核销只使用扣除售后冻结后的可核销数量。订单归属、履约前置仓和仓库沿用订单事实，不允许弹窗改仓。
- 快递整单发货及运单更正复用既有接口。批量发货继续保留。
- 订单核销入口把凭证绑定到路径中的订单，服务端在锁定订单后核对凭证归属、有效期、数量、权限与修订。

## 请求恢复

提交前将原请求和幂等键存入当前浏览器会话存储。网络中断、超时及服务端结果待定时冻结正文，禁止编辑后当作新请求提交。列表和详情显示“核查操作结果”入口，先读取最新订单，再沿用原请求重试。

恢复记录必须匹配当前操作员、订单、动作、路径及字段白名单；收款确认阶段还须匹配当前订单中原操作员的收款记录、账户、流水、金额、时间及备注。存储不可用、记录损坏或归属不一致时阻止写入并提示核查。

## 后端入口与迁移

| 入口 | 权限与用途 |
| --- | --- |
| `POST /api/v1/admin/orders/{id}/local-fulfillment` | `fulfillment.ship`；仅 `PREPARE / DISPATCH / COMPLETE`，需要修订号与幂等键 |
| `POST /api/v1/admin/orders/{id}/pickup-preview` | `fulfillment.ship`；核验自提凭证和当前订单修订 |
| `GET /api/v1/admin/orders/{id}/tracking` | `order.read` 或 `fulfillment.read`；读取已有轨迹缓存及渠道结果 |
| `POST /api/v1/admin/orders/{id}/wechat/query` | `payment.offline.confirm`；复用可信微信查单服务 |
| `POST /api/v1/admin/orders/{id}/redemptions/{voucherId}/use` | `fulfillment.redeem`；核销凭证必须属于当前订单 |

迁移 `fulfillment.0009_admin_local_delivery_actor` 允许履约事件记录后台管理员，并约束会员和后台操作员恰有一方。后台订单详情展示操作员、时间、说明与原请求标识；客户响应不暴露内部履约事件说明。

订单列表摘要附加 `redeemEligible / hasShipment`，在已有批量查询中计算，供列表展示核销、物流与运单更正入口。`GET /orders?orderIds=...` 支持 1–100 个不同 UUID，筛选在计数与分页前执行，并与既有权限、会员归属和其他条件叠加。联盟列表按当前页订单编号精确读取操作摘要，避免依赖两套列表的排序一致性。

## 工程检查点

1. **责任边界**：账号域复核登录身份和实时权限，订单域读取快照，履约与支付域复用已有业务入口；PC 只收集操作事实和呈现结果。
2. **权限**：服务端拒绝未知动作，锁等待后重新验证权限；前端按钮隐藏不能代替服务端授权。
3. **并发**：写操作带当前修订与原幂等键，事件、审计与业务变更同事务；重复请求不增加事件或审计。
4. **库存和资金**：不直接写库存或付款状态，沿用售后、库存和可信资金服务。
5. **失败恢复**：冻结原正文并核查结果，避免超时后创建新收款或交付事实。
6. **兼容**：保留旧 `auth/confirm` 入口及历史确认表供旧客户端兼容；确认令牌不再作为业务接口的授权条件。原会员履约与核销入口保留。
7. **验收**：账号授权、密码设置、订单状态、售后冻结、重复请求、事务回滚、桌面与窄屏界面分层验证；发布状态以实际 Git 和部署回执为准。

- 后台相关 12 个模块 858 项回归通过；账号单独 59 项通过，免密码授权与密码设置修改文件合计覆盖 87%。
- 履约接口、会员兼容与审计回滚 35 项通过；新增服务与接口分支覆盖 93%。列表能力标识、精确订单编号筛选及履约待办读取另有 18 项数据库回归通过。
- `npm test`：111 项逻辑测试、542 项组件测试、TypeScript 检查及 Vite 构建通过。订单弹窗 34 个组件场景覆盖语句 95.65%、分支 91.96%、函数 96%、行 96.87%。测试工作进程限制为 4，避免与本地服务并行时过度启动 DOM 工作进程造成超时。
- 模拟浏览器：免密码操作相关桌面与 390px 窄屏 20 项、订单弹窗相关 10 项通过。
- 真实隔离本地后台：无操作确认令牌的备货原请求重放只产生一次事件、一次修订；浏览器完成实际收款登记、备货、配送、送达，重新读取确认状态与操作历史持久化；最终预览还完成一份核销和整单自提，刷新结果保持一致。这里的银行流水和商品均为测试种子，没有真实银行或微信资金。
